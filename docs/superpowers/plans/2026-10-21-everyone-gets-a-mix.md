# Plan: everyone gets a mix

Date: 2026-10-21. Spec: `../specs/2026-10-21-everyone-gets-a-mix-design.md`.
Decisions: pending (five listed at the end of the spec); record them in
`../../decisions.md` when taken.

House cadence: one fresh implementer per task, red tests first, then a
reviewer pass and one fix round. Implementers and reviewers run on Opus at
medium effort. At most two agents in flight. One commit per task, files
staged by explicit path; the drizzle journal is staged with only this
program's entries when another program's migration is in the tree.

## Standing rules for every task

- **Free plan.** 50 subrequests and 10 ms CPU per invocation, 5 cron
  triggers, 10,000 Workers AI neurons a day, Neon 100 CU-hours a month and
  0.5 GB storage. No task assumes a paid limit without a decision.
- **Shared working tree.** Other sessions may hold uncommitted work. Edit
  in place; no stash, checkout, restore or reset; stage by explicit path.
- **No production writes, no deploy, no migration apply** unless a gate says
  the founder runs it. Deploys from a clean worktree of committed HEAD.
- New listener-facing strings and DJ prose have no em dashes; the guard in
  `server/test/dj/no-em-dash.test.ts` covers new exported strings.
- Never store lyric text. Curation tests are golden-set structural
  assertions.
- Docs ride with the change: spec status line per step, `docs/backlog.md`.
- Never run a formatter over a folder; only over files the task created or
  edited.

## Step 1: a fair floor

### Task 1: artist keys

Files: `server/src/db/schema.ts`, new migration (next free number),
new `server/src/dj/artist-keys.ts`, `server/test/dj/artist-keys.test.ts`.

- `artistKey(name)`: lowercase, NFKD then strip combining marks, drop
  everything but letters and digits. `creditedArtists(credit)`: split on
  `&`, `,`, `feat.`, `ft.`, `with`, ` x ` (word-bounded), trim, drop empty.
- `tracks.artist_keys text[]` generated by a Postgres function
  `artist_keys(text)` that mirrors the two helpers (an `unaccent`-free
  `translate` table for the Latin diacritics the catalogue actually holds,
  listed in the test), plus a GIN index. The migration is a function, a
  generated column and an index; check by hand.
- Tests: table-driven pairs ("jay z" / "Jaÿ-Z", "beyoncé" / "beyonce",
  "¥$, kanye west & ty dolla $ign" credits three artists, "drake x future"
  two); the SQL function agrees with the TypeScript helper on the table
  (pglite).

Task 5 measured on pglite (200 rows): the table with its HNSW index goes
from 2,867,200 to 1,171,456 bytes (0.41), which projects production's
76 MB to about 31 MB and 25,000 rows to about 130 MB. Precision: fp16
moves a cosine distance by about 5e-6 (max 3e-5 in a 6,000-vector
simulation), far below the meaning term's weight; only candidates already
tied can swap. Order at Gate 3: run 0043 first, then deploy, because the

## Step 4: never refuse, reshaped 2026-10-22

### Task 7: model-proposed songs verified on Apple

Files: new `server/src/dj/propose.ts`, `server/src/dj/loop.ts`,
`server/src/dj/curate.ts` (shared reason rules), `server/src/albums/verify.ts`
(export `artistMatches`, or move it and `fold` to a shared module),
`server/src/index.ts` (`NEVER_REFUSE` var), `server/wrangler.jsonc`,
`server/src/seeds/contracts.ts` (`proposed_mix` funnel type, migration for
the CHECK), tests beside each.

- `proposeSongs(llm, { brief, intent, seeds, storefront })`: one model
  call with the DJ system prompt's voice rules, returning `{ title, artist,
  reason }[]` of `targetCount + 8`, parsed with the same strict-JSON guard
  as curation; reasons go through the existing reason sanitiser (140
  characters, no em dashes, never naming the track or artist).
- `verifyProposals(catalog, db, { proposals, storefront, budget: VERIFY_MAX
  25, deadlineMs: VERIFY_DEADLINE_MS 10_000 })`: one `searchSongs` per
  proposal, keep the first hit whose credited artist key and title key
  match, insert through `addCatalogueSongs` with the boost and no
  enrichment, return the verified rows in proposal order with their
  reasons and the misses.
- Loop: when `NEVER_REFUSE` is on, the mode is `insufficient_seeds` after
  Task 2 and the fill's insertion, and the listener is not personal: run
  propose and verify instead of the pool and curation; if fewer than
  `MIN_VERIFIED` (8) verify, one replacement proposal naming the misses;
  if still short, the DJ reply says what it could confirm and offers to
  loosen. Build the queue from the verified rows in order, cut to
  `targetCount`, mark the session `not_personal`, and prepend a
  `PROPOSED_NOTICE` to the reply (DJ's own knowledge, checked against Apple
  Music, not the listener's listening). The fill's in-request enrichment
  is skipped on this path; its top-songs insertion stays.
- Funnel: `proposed_mix` on the listener; counts (`proposed`, `verified`,
  `searches`) on the `dj turn` log line.
- Flag off: today's behaviour, pinned by a test.
- Tests (golden structural, no exact tracks): a no-library listener with
  unknown artists gets a full queue of verified rows in proposal order; a
  proposal Apple cannot confirm is dropped; title-only matches (a cover)
  are rejected; the replacement round runs once; short verification gives
  the loosen reply; budget and deadline respected; verified rows are
  inserted once with the boost; nothing changes for corpus or personal
  listeners; no provider buttons or copy regressions; the notice has no
  em dashes.
